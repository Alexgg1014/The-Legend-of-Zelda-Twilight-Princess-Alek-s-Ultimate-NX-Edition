# V1.1 CPU plan (and the gfx service on deko3d)

For V1.1 only: nothing here goes into V1.

Sources:

## What the data says first

The newest sampler profiles are from rc12 on the console (`SWITCH-TEST-V1-RC12/consola-20261019-rc12/profile-*.txt`):
- 148 369 samples at about 1 ms each, over five zones, sampling the game's main thread;
- symbolised against `dusklight-v1rc12.elf` by `rank_profile.py` (in the scratchpad; it should move to `platforms/switch/tools/`).

| Hyrule Field (29 619 samples) | self |
|---|---|
| waiting: `svcSleepThread` 29.5 %, `svcWaitProcessWideKeyAtomic` 17.7 %, locks and signals 3 % | **≈ 50 %** |
| GX command emission (`GXCmd1u32`, `GXLoadTexObj`, `GXSetArray`, `GXPosition3f32`…, `aurora::gx::fifo::publish`) | 10.1 % |
| J3D calc and animation (`J3DMtxBuffer::calcWeightEnvelopeMtx`, `J3DJoint::recursiveCalc`, `J3DAnmTransformKey::calcTransform`, `J3DGetKeyFrameInterpolation`) | 4.9 % |
| math: `C_MTXConcat` 2.7 %, `C_MTXMultVec`, `C_MTXCopy`, PSVEC/mDoMtx | 4.3 % |
| collision: `dBgWKCol::GroundCross`, `cBgS::GroundCross`, `dBgS::WallCorrect` | 4.0 % |
| `memmove` | 2.4 % |
| process lists: `cNdIt_Judge`, `fpcSch_JudgeByID` / `fpcSch_JudgeForPName` (linear actor searches) | 1.5 % |

So in the heaviest zone the main thread waits about half the time. The cap there is not the game's own CPU work: it is what the main thread waits for, which is the render worker, the GPU or vsync.

Speeding up the math library alone can win at most a few percent of the main thread. It only turns into frames once the wait shrinks.

**First step for V1.1:** take a fresh profile of the PGO build (rc19) with the render worker sampled too, and split the wait by what is waited on. This is ak's "profile the PGO build" first.

## Methods (from Chansey's notes, adapted)

1. **Instruction-level view of hot functions.** For each hot function, show the sampled PCs against its disassembly (the build's ELF, `objdump -d`, the PCs as offsets), so we can tell work that can be removed from waiting on memory.
   - A sampler PC parked on one load after a cache miss calls for data layout or prefetching, not rewriting.
   - It is a small script on top of `rank_profile.py`.
2. **Marker functions as a yardstick.** Pick a few functions no change touches, e.g. `cNdIt_Judge` and `dBgWKCol::GroundCross`, and compare their sample share between runs. A change that moves them changed the scene load, not the code under test. This makes A/B runs on the console comparable without identical routes.
3. **Verify mode for leaf rewrites.** A `perf-lab.ini` key runs the original function after the rewrite, compares the outputs bit for bit, and logs the first difference. It is off in release. Bit-exactness matters because the game's physics and animation are deterministic over many frames.
4. **Frame-hash lockstep** for everything that is not a leaf: hash the GX command stream per frame (or the EFB with a fixed seed and replay) on the Check Tour's fixed spots, before and after.

## Ranked candidates

1. **What the main thread waits on** (about 50 % in Hyrule Field). Profile the render worker and the GPU in the same run, then attack whichever is the cap:
   - render worker CPU (`render: worker_cpu` in the heartbeat);
   - GPU time;
   - the FIFO handoff.
   The fifo-opt notes list what V1.1 needs here (async end of frame, which was judged too risky for V1).
2. **GX command emission** (10 %): `GXCmd1u32` and the immediate-mode vertex calls (`GXPosition3f32`, `GXColor4u8`, `GXTexCoord1x8`, `GXNormal1x8`), grass and flower packets.
   - Batch writes into the FIFO buffer (one bounds check per primitive instead of per value).
   - Display lists for static immediate-mode geometry (grass, flowers, `dKyr_drawStar`).
   - Output stays identical, so the frame hash checks it.
3. **J3D skinning and animation** (5 %): `calcWeightEnvelopeMtx`, `recursiveCalc`, key-frame interpolation.
   - NEON for the 3×4 matrix blends, with the original's operation order.
   - **No FMA contraction unless the original fused** (`-ffp-contract=off` on those units, as the game's own float semantics need).
   - Checked by verify mode.
4. **Math library** (4 %): `C_MTXConcat`, `C_MTXMultVec`, `C_MTXCopy`, PSVEC.
   - Hand NEON with exact rounding (the same operation order, no FMA unless the original used it).
   - These are leaves, which verify mode covers well.
   - Small on its own, but it is the safest first piece and the template for item 3.
5. **Collision** (4 %): `GroundCross` and `WallCorrect`, but measure first with the instruction view. Likely memory-bound (BVH walk), in which case it calls for layout, not NEON.
6. **memmove** (2.4 %): find the callers (the f1/f2 frame records in the profile). Big copies may be avoidable (double buffers); small ones want a NEON `memcpy` from libnx/newlib, if it isn't one already.
7. **Linear actor searches** (1.5 %): `fpcSch_JudgeByID` / `fpcSch_JudgeForPName` over the process list. Use an id → process map maintained on create and delete, behind a key, with verify mode comparing against the linear search.

## How each step ships

- One `perf-lab.ini` key per change, off until it is measured on the console, then on.
- Verify mode (leaves) or frame hash (others) before it is turned on.
- Measured with the Quality tour and the marker functions, against the same PGO profile.
- The profile is regenerated once several changes are in: PGO profiles go stale as code changes.
- Hook targets: rewriting a function a mod hooks keeps its symbol and entry. The hook-inline gate stays a hard gate.

## Also for V1.1: the gfx service on deko3d

For V1, a mod that draws with the gfx service keeps the "needs Vulkan: restart?" prompt under deko3d (Alex, 2026-10-22). Running it on deko3d is a V1.1 item.

**What the service is.** It doesn't take draw commands from the mods. It hands them the WebGPU device (`GfxService.get_proc_address` returns `wgpu*` functions), and the mods create their own objects through it:
- shader modules from WGSL source;
- render and compute pipelines;
- bind groups, samplers and buffers.
They then draw from stage hooks and draw callbacks.

**Who uses it** (catalog snapshot 2026-10-22, `wgpu*` imports in each mod's library):

| Mod | `wgpu*` functions | Notes |
|---|---|---|
| Twilit Essentials 2.8.4 | 13 | shader modules, render pipelines, samplers, bind groups, draws: its WGSL post-effects (vignettes, graphics grade) |
| Dawnlight 5.1.0 | 33 | includes compute passes |
| interlacing 1.2.0 | 36 | its own render passes, buffers |
| vbao 1.1.0 | 26 | compute |
| dof_hq 1.1.0 | 15 | pipeline layouts of its own |
| deferred_fog 2.0.0 | 11 | |
| albw 0.3.0 | 11 | |
| gz 0.2.3 | 0 | uses the service, no raw `wgpu*` |

**What it takes on deko3d.**
1. A WebGPU subset on top of deko3d:
   - the object model (devices, pipelines, bind groups, samplers, buffers, textures);
   - the pipeline state;
   - render and compute passes, recorded into the deko3d command stream like Aurora's own draws.
2. Shader compilation at run time, WGSL to Maxwell code in a DKSH. That is the hard part: our deko3d shaders are compiled offline (uam), and there is no on-console compiler for this today. The one path in reach:
   - **naga** turns WGSL into SPIR-V (we already ship naga);
   - **Mesa's NVK compiler**, which is inside our `libvulkan.a`, turns SPIR-V into Maxwell code;
   - we wrap the result as a DKSH.
   This is research: the NVK compiler's entry points, its output and DKSH's header and resource layout all need checking first.
3. Caching the compiled shaders by the hash of their source (same rules as the boot caches).

The size is weeks, not a release candidate. Dawnlight's compute means the subset can't stop at fullscreen post-effects.

**Before then:** under deko3d, a mod that asks for the gfx service gets the prompt, and the next start uses Vulkan.
